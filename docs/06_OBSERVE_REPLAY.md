# 06 OBSERVE / REPLAY — 관측 자료 형식과 사고 재현 장치

버전: v1 (2026-11-10)

관련 불변식: I8, I9, I11, I12 / 관련 문서: 01 (저널 J1~J5), 03 (데이터 배분 2-4), 04 (PM10, 환경 모델)

## 0. 목적과 원칙

- 가동 후 진단은 추측이 아니라 자료로 한다(design-first 4장). 사고는 기록으로 재구성하고, 재생 장치로 재현한 뒤에 고친다.
- 기록은 세 종류다. 저널(진실의 원장, 버리지 않음), 로그(진단용, 상한 있음, 버릴 수 있음), 지표(분 단위 집계).
- 재현성 원칙: 같은 입력 기록과 같은 코드 버전을 넣으면 같은 저널과 같은 출력이 나와야 한다.

## 1. 제어면과 데이터면 분리

| 구분 | 내용 | 실행 | 기록 |
|---|---|---|---|
| 제어면 | OrderGateway, AdmissionGate, SubscriptionManager의 구독 상태, ModeController, AuthManager, ConnSupervisor | 스레드 하나의 이벤트 루프. 액터는 그 안의 논리 단위다(I9) | 모든 입력과 출력을 전역 순번으로 기록 |
| 데이터면 | 시세·틱 배분(03 2-4), 화면 갱신, 전략 계산, 백테스트 | 별도 스레드·작업자 | 기록하지 않음. 결손·넘침만 제어면 사건으로 보고 |

- 전략(L3)의 출력인 의도(intent)는 제어면 입력으로 기록한다. 그래서 주문 쪽 사고는 시세 없이 재현된다.
- 틱은 선별 종목만 별도로 저장한다(HANDOFF 2장 전제). 전략 재생(5-3)에만 쓴다.
- 제어면 루프는 저널 fsync(01 J2) 외에는 막히는 I/O를 하지 않는다. 로그 쓰기, 화면 통지는 큐에 넣고 바로 돌아온다.

### 1-1. 재현성 규칙

| 번호 | 규칙 | 막는 문제 |
|---|---|---|
| RP1 | 제어면은 벽시계를 읽지 않는다. 단조 시계 값은 주입된 시계에서만 읽고, 읽은 값은 입력과 함께 기록한다(I12) | 재생 때 시각이 달라짐 |
| RP2 | 타이머 발화는 입력 사건으로 기록한다(타이머 종류, 대상, stateEpoch) | 재생 때 타이머 순서가 달라짐 |
| RP3 | 난수(백오프 흔들림)는 기록된 시드에서만 만든다. 시드는 세그먼트 머리에 기록한다 | 재생 때 백오프 시각이 달라짐 |
| RP4 | 결과가 순회 순서에 좌우되는 곳에는 순서가 정해진 자료구조만 쓴다 | 해시맵 순회 순서 차이 |
| RP5 | 세그먼트 머리에 코드 버전(git 커밋), 설정 해시, 계좌·환경 표식(가린 값)을 기록한다. 버전이 다르면 재생은 "참고용"으로만 표시한다 | 다른 코드로 재생해 엉뚱한 결론 |

## 2. 기록 종류와 형식

저장 위치: `lab-data/run/YYYY-MM-DD/` (`.gitignore`의 `lab-data/`에 포함, 커밋되지 않음)

| 파일 | 내용 | 형식 | 버림 | 쓰기 |
|---|---|---|---|---|
| `journal.jsonl` | 주문 상태 전이 (01 J1~J5) | JSON Lines | 절대 안 버림 | 01 J2: S는 fsync 후 전송 |
| `input-NN.jsonl` | 제어면 입력 전부: REST 응답, WS 주문·잔고 통보, 세션·토큰 사건, 타이머, 의도, 사람 조작, 데이터면 결손 보고 | JSON Lines, 세그먼트 NN은 재시작마다 +1 | 안 버림 | 묶음 fsync (Tf마다). 크래시로 마지막 묶음이 사라져도 대조(I11)가 진실이다 |
| `output-NN.jsonl` | 제어면 출력 전부: 주문·취소 전송, 조회 요청, WS 등록·해제, 모드 전환, 알람 | JSON Lines | 안 버림 | 묶음 fsync |
| `app.log` | 사람이 읽는 로그 (WARN 이상 기본) | 텍스트 한 줄 1건 | 2-2 규칙으로 버림 | 비동기 |
| `flight/<시각>-<사유>.jsonl` | 블랙박스 덤프 (2-3) | JSON Lines | - | 사고 때 1회 |
| `metrics.csv` | 1분마다 1줄 | CSV | 안 버림 | 비동기 |
| `ticks/<종목>.bin` | 선별 종목 틱 | 압축 | 용량 상한 | 데이터면 |

### 2-1. 공통 필드 (input, output, journal)

| 필드 | 의미 |
|---|---|
| seq | 전역 순번. 제어면 루프가 입력을 꺼낼 때 붙인다. 세그먼트 안에서 빈틈 없이 증가 |
| mono | 주입 시계의 단조 시각 (ms) |
| kind | 사건 종류 (01·02·03 표의 사건 이름과 같은 영문 코드) |
| actor | 처리 액터 |
| key | intentKey, 구독 키, 조회 키 중 해당하는 것 |
| ord | 주문번호 (있으면) |
| e, h, ep | 소켓 세대, 토큰 세대, stateEpoch |
| body | 필요한 필드만 추린 본문 (2-4 가림 규칙 적용) |

### 2-2. 로그 규칙 (PM10 대응, I8)

| 번호 | 규칙 |
|---|---|
| LG1 | 로그 호출은 상한 Ql인 큐에 넣고 즉시 돌아온다. 제어면·데이터면 어느 쪽도 로그 쓰기를 기다리지 않는다 |
| LG2 | 등급별 차선: ERROR·WARN 차선은 따로 두고 예약분을 남긴다. 큐가 넘치면 DEBUG → INFO 순으로 버리고 버린 수를 센다. 버린 수는 1분마다 한 줄로 남긴다 |
| LG3 | 반복 억제: 같은 (등급, 위치, 메시지 틀)이 Tdup 안에 반복되면 첫 줄만 쓰고, 창이 끝날 때 "N회 반복" 한 줄을 쓴다 |
| LG4 | 디스크에는 WARN 이상만 기본으로 쓴다. DEBUG·INFO는 메모리 링 버퍼(최근 Tring초)에만 둔다 |
| LG5 | 파일 상한: 하루 파일 크기 상한 Smax, 보관 일수 Dkeep, 전체 상한 Stot. 넘으면 오래된 것부터 지운다. 저널과 input·output은 이 규칙으로 지우지 않는다 |
| LG6 | 디스크 여유 감시: 여유가 Hwarn 아래로 내려가면 디스크 로그를 ERROR만 남기고 알람. Hcrit 아래면 로그 디스크 쓰기 정지. 저널 몫 공간이 남도록 Hcrit은 하루 저널 최대량의 몇 배로 잡는다. 로그 쓰기 실패는 매매를 멈추지 않는다. 저널 쓰기 실패는 01 J5를 따른다 |
| LG7 | 화면 로그 창은 최근 Nui줄만 Fui 주기로 읽는다. 화면이 로그 파일 전체를 읽지 않는다 |

### 2-3. 블랙박스 덤프

- 사건: 모드 하향(ARMED에서 내려감), 종목 HALT, 전역 HALT, 실행 시점 검사 위반(3장), 사람이 누른 "기록 남기기".
- 내용: 링 버퍼의 최근 Tring초 DEBUG 로그 + 최근 제어면 입력·출력 Nflight건 + 현재 모드, 주문 상태 요약.
- 같은 사유의 덤프는 Tflight 안에 1회만 만든다. 덤프는 비동기로 쓴다.

### 2-4. 비밀정보 가림 (AGENTS.md 절대 규칙)

- 가림은 내보낼 때가 아니라 기록하는 순간에 한다. 어떤 파일에도 원문 비밀정보가 남지 않는다.
- 토큰, 앱키, 시크릿: 기록하지 않는다. 토큰은 세대 번호 h로만 남긴다.
- 계좌번호: 뒤 4자리만 남긴다.
- `.env` 내용과 HTTP 인증 헤더는 어떤 등급의 로그에도 쓰지 않는다.

## 3. 실행 시점 검사 (TLC 속성의 가동 중 판정)

TLC는 모델을 검사하고, 이 검사는 실제 프로그램을 검사한다. 제어면 루프가 매 사건 처리 뒤 확인한다.

| 검사 | 출처 | 위반 시 |
|---|---|---|
| NoDoubleSubmit, NoResendAfterAmbiguity | 01 | 전역 HALT, 덤프 |
| CumMonotonic, NoOversell | 01 | 해당 종목 HALT, 덤프 |
| SingleUnresolved | 01 | 해당 종목 HALT, 덤프 |
| SingleIssuer, BoundedIssueRate | 02 | 토큰 D, SAFE, 덤프 |
| SingleCtlInFlight | 03 | 해당 구독 키 정지, SAFE, 덤프 |
| RateBound, OrderRateBound | 03 | SAFE, 덤프 |
| seq 연속성 (세그먼트 안 빈틈 없음) | 06 | 경고, 덤프 |

검사 위반은 설계나 코드의 결함이다. 덤프와 함께 design-first 5장에 기록하고 4장 진단 절차를 밟는다.

## 4. 진단 요약 (채팅 전달용, E08 대응)

- 메뉴 "진단 요약 만들기"(사고 시각 또는 덤프 파일 선택) → `diag-<시각>.txt` 생성, 클립보드 복사.
- 길이: 40줄 이하로 고정. 사용자는 이 파일 내용만 채팅에 붙인다. AI는 다른 출력을 요구하지 않는다. 더 필요하면 키(종목, intentKey, seq 범위)를 지정해 다음 요약을 요청한다.
- 형식
  - 1줄: `INCIDENT <시각> <사유> mode <이전>-><이후> commit <sha> cfg <해시>`
  - 2줄: `COUNTS orders <n> fills <n> u <n> halt <n> gate-reject <n> log-drop <n>`
  - 3줄 이후: `seq mono kind key ord detail` 형식의 사고 전후 사건. 사고 키와 관련된 줄을 먼저 넣고, 나머지는 같은 시간대의 경고만 넣는다.
- 2-4 가림이 이미 적용된 자료에서 만든다.

## 5. 재생 장치 (가짜 브로커)

### 5-1. 재현 재생

1. 같은 날짜의 `input-NN.jsonl`을 순번대로 제어면 커널에 넣는다. 시계, 타이머, 시드는 기록값을 쓴다(RP1~RP3).
2. 커널이 만든 저널과 출력을 기록된 `journal.jsonl`, `output-NN.jsonl`과 비교한다.
3. 결과: `SAME` 한 줄, 또는 `DIVERGE seq <n> expected <...> got <...>` 한 줄. 첫 갈림만 보고한다.
4. 세그먼트가 여러 개이면(재시작) 각 세그먼트를 J4 재생부터 시작해 따로 재생한다.

### 5-2. 교란 재생 (환경 모델 퍼징)

- 기록된 하루치 입력에 04 환경 모델의 EV01~EV04(뒤바꿈, 중복, 유실, 지연)를 시드별로 섞어 넣는다. 응답은 가짜 브로커가 만든다.
- 3장 검사가 모든 시드에서 위반 0이어야 한다. 위반이 나면 시드와 첫 위반 순번을 한 줄로 낸다. 같은 시드로 다시 돌리면 같은 위반이 나온다.
- 01·03·04의 수용 시나리오(T, S, V)는 이 장치 위에서 대본으로 실행한다.

### 5-3. 전략 재생

- 선별 종목 틱 → 같은 전략 코드(`reset`/`update` 계약, kiwoom-desk 전략 계약) → 의도 목록.
- 그날 실제로 기록된 의도와 비교해, 가동 중 신호와 재생 신호가 다르면 `INTENT-DIFF` 목록을 낸다. 차트·백테스트·실매매 신호 일치를 확인하는 장치이며, Strategy Lab 챔피언–도전자 비교(HANDOFF 3장)의 입력이 된다.

## 6. 지표 (`metrics.csv`, 1분 1줄)

모드, 차선별 허가 사용량과 큐 길이, BUSY·TIMEOUT 수, 유량 거절 수, 주문 응답 지연 p50·p99, 체결 통보와 REST 응답 시차, WS 메시지 간격 최대값, 구독 등록 수, 데이터면 결손 수, 로그 버림 수, 디스크 여유, 제어면 루프 지연 최대값. 05 실측 계획의 원자료로도 쓴다.
