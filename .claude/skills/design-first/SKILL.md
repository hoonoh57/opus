# design-first

## 1. 원칙

- 사고는 설계 단계에 집중한다. 코딩은 설계서를 그대로 옮기는 일이다(AGENTS.md 2장).
- AI는 설계를 쓴 뒤 스스로 공격해 고친 다음에 내놓는다. 공격 결과는 문서의 "자체 공격으로 고친 곳" 표와 사용자 보고에 남긴다.
- 최종 판정은 기계(TLC, 검사 스크립트, 재생 테스트)가 한다. AI의 "문제없음"은 판정이 아니다.
- 결함은 장부(5장)에 누적하고, 점검표(3장)를 키운다. 같은 종류의 결함이 두 번 나오면 점검표가 실패한 것이다.

## 2. 설계 절차

1. 그 세션에서 `docs/00_LAWS.md`와 관련 문서를 원문으로 다시 읽는다. 기억으로 설계하지 않는다.
2. 범위, 액터(쓰기 주체), 최악 가정을 먼저 적는다.
3. 상태 × 사건 전이표를 빈칸 없이 쓴다. 불가능한 칸도 "HALT" 또는 "무시, 로그"로 명시한다.
4. 3장 점검표 A~L을 항목마다 실제로 적용한다. 해당 없음도 이유를 한 줄로 쓴다.
5. 고친 곳을 "자체 공격으로 고친 곳" 표에 남긴다(공격 / 고치기 전 / 고친 뒤).
6. 수용 시나리오(사람이 읽는 기대 결과)와 TLC 속성(기계 판정)을 쓴다.
7. 실측이 필요한 값은 "미확정 사항" 표에 최악 가정과 확정 방법을 함께 적는다. 법칙에 숫자를 넣지 않는다(00 3장).
8. INDEX.md 상태, HANDOFF.md 변경 기록을 같은 커밋에서 고친다.
9. 사용자 보고는 "점검에서 고친 곳" 중 중요한 것 3~4개만 짧게 쓴다.

## 3. 자체 공격 점검표

| 번호 | 공격 질문 | 실제로 잡은 결함 (5장) |
|---|---|---|
| A 사건 누락 | 모든 상태에 늦은 응답, 중복, 이전 세대 메시지, 타이머, 재시작, 사람 리셋 열이 있는가? 종료 상태에도 늦은 체결이 오는가? | D04, D06 |
| B 순서 역전 | 응답과 통보가 반대 순서로 오면? 같은 키의 제어 메시지 두 개가 동시에 나가 뒤바뀌면? | D08, D17 |
| C 검사 시점 | 조건을 넣을 때 검사하고 실행할 때는 검사하지 않는가? 대기 중에 조건이 바뀌면? | D16, D19 |
| D 모호성 | 결과를 모르면 재전송하지 않고 U로 가는가? 매칭 후보가 0개, 1개, 2개 이상일 때 각각 정의돼 있는가? 매칭 대상에 들어가면 안 되는 상태(미전송 등)가 섞이지 않는가? | D07, D10, D11 |

| F 자원 상한 | 모든 큐와 버퍼에 상한과 기한이 있는가? 대량 작업이 핵심 요청(취소)을 굶기지 않는가? 넘치면 어느 모드로 가는가? 외부로 나가는 행위(주문 수, 진입 수, 발급 수) 자체에도 횟수 상한이 있는가? 키 단위 중복 방지는 횟수 상한이 아니다. | D18, D20, D21 |
| G 데이터 유형 | 상태형(최신값만)과 사건형(유실 금지)을 바르게 나눴는가? 유실을 감지하면 무엇을 막는가? | D17 |
| H 문서 간 모순 | 다른 문서의 같은 주제 규칙과 충돌하지 않는가? 규칙의 유일한 출처가 정해져 있는가? 예외는 원 규칙에 명시했는가? | D09, D12 |
| I 대응의 부작용 | 장애 대응(소켓 종료, 정지)이 꼭 필요한 기능(체결 통보 수신, 취소)까지 끊지 않는가? | D14 |
| J 재시작·복원 | 재시작 직후 대조 전에 무엇이 허용되는가? 복원이 한꺼번에 몰려 유량 위반 → 재복원 무한 반복이 생기지 않는가? | D03, D18 |
| K 늦은 의도 | 막혀 있던 동안 생긴 신호, 요청이 해제 뒤 뒤늦게 실행되지 않는가? | D19 |
| L 타이머 경합 | 상태가 바뀐 뒤 이전 상태의 타이머가 울리면? 세대(stateEpoch) 판정이 있는가? | D05 |
| M 프로세스 경계 | 같은 키, 같은 계좌를 다른 프로세스나 다른 프로그램이 동시에 쓰면? 이중 실행을 막는가, 막을 수 없으면 탐지하는가? | D21 |
| N 재현성·관측 | 이 사고를 기록만으로 재현할 수 있는가? 벽시계, 난수, 순회 순서, 스레드 순서에 결과가 좌우되지 않는가? 관측(로그·덤프)이 매매를 막거나 디스크를 빼앗지 않는가? 기록에 비밀정보가 남지 않는가? | - (06 작성 시 신설) |

## 4. 코딩 착수와 가동 후 진단

- 착수 판단은 HANDOFF.md 7장 "코딩 착수 관문"을 따른다. 관문을 하나라도 통과하지 못하면 코딩하지 않는다.
- 가동 후 사고 진단 순서
  1. 저널, 로그, 화면 기록으로 사건 순서를 재구성한다(06 형식).
  2. 재생 장치에서 사고를 재현한다. 재현하지 못하면 추측으로 고치지 않고 관측을 늘린다.
  3. 원인이 설계 결함이면 설계 문서를 먼저 고치고 5장에 기록한 뒤, 수용 시나리오와 TLC 속성을 추가한다.
  4. 그다음에 코드를 고친다. 코드만 고치는 땜질은 금지한다.

## 5. 설계 결함 장부

커밋 뒤에 사람, TLC, 가동 사고로 발견된 결함을 적는다. 자체 공격 단계에서 고친 것은 각 문서 표에 남기고 여기에는 적지 않는다. 새 결함이 기존 항목으로 잡혔어야 했다면 그 항목 질문을 더 구체적으로 고치고, 어느 항목에도 해당하지 않으면 새 항목을 만든다.
