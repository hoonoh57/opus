# design-first

## 1. 순서 (건너뛰지 않는다)

설계 → 자체 공격 → 기계 판정(TLC, 재생 테스트) → 코딩 → 장중 실데이터 확인.
코딩 중에 설계 빈칸이 보이면 코딩을 멈추고 설계 문서부터 고친다.

## 2. 설계 문서에 반드시 들어갈 것

1. 막는 사고: `docs/04` 사전 부검표의 행 번호. 04 작성 전에는 HANDOFF 1장의 5대 사고(주문 폭주, 체결 역전 재주문, 유량 위반 리셋, 중복 요청 자원 고갈, UI 멈춤) 중 무엇인지.
2. 지키는 불변식 번호(`docs/00_LAWS.md`의 I1~).
3. 상태 × 사건 완전 전이표. 빈칸 없이, 불가능한 전이도 처리(HALT 등)를 적는다.
4. 사건 열에 타이머 만료, 재시작, 중복, 순서 뒤바뀜, 유실을 포함한다.
5. 수용 시나리오(T번호)와 각 기대 결과.
6. 미확정 값 표: 실측 전에는 최악 가정값을 쓰고 표시한다.

## 3. 넘기기 전 자체 공격 점검표

2026-11-09에 사용자가 붙여넣은 뒤에야 발견된 실제 결함에서 뽑았다. 문서를 주기 전에 모든 행을 확인한다.

| 점검 | 실제로 놓친 사례 |
|---|---|
| 모든 상태가 매칭·조회·대조 규칙에 빠짐없이 들어갔나 | 01: R 상태 주문이 고아 버퍼 대조 매칭에서 빠짐 |
| 재전송 뒤 늦게 도착한 옛 응답을 처리하나 | 01: 취소 재전송 뒤 늦은 거부가 잘못된 HALT 유발 |
| 같은 문서 안의 규칙끼리 모순이 없나 | 01: J5와 J2 충돌 |
| 각 시나리오를 전이표로 한 칸씩 따라가 기대 결과가 맞나 | 01: T16 기대 결과 오류 |
| 행동 전에 선행 자원(토큰, 세션)이 준비됐는지 확인하나 | 02: 토큰 확인 없이 LOGIN 전송 |
| 같은 이름이 다른 의미로 쓰이지 않나 | 02: 실패 카운터 n 혼용 |
| 다른 문서(00 불변식, 01~03)와 충돌이 없나 | 교차 확인 |

발견한 결함은 고친 뒤에 넘기고, 새 유형이면 이 표에 행을 추가한다.

## 4. 기계 판정

- TLC: 사용자 PC(Java)에서 실행하고 출력만 채팅에 붙인다. 위반이 나오면 출력된 사건 순서를 수용 시나리오에 추가하고 설계를 고친다.
- 재생 테스트: 저널을 가짜 브로커로 재생해 사고를 재현한다(`docs/06`).

## 5. 코딩 착수 판단

`HANDOFF.md` 7장 관문을 전부 충족할 때만 코딩을 시작한다. 하나라도 비면 "무엇이 비었는지"와 "채우는 다음 행동"을 답한다.

## 6. 가동 후 진단

1. 저널·로그로 사고를 재현한다(재현 전에는 고치지 않는다).
2. 원인을 설계 문서의 어느 칸이 틀렸거나 비었는지로 특정한다.
3. 설계 → 시나리오 추가 → 기계 판정 → 코드 순으로 고친다.
4. 같은 유형이면 3장 점검표에 추가한다.
